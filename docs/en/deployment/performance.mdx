---
title: "Memory and sizing"
description: "Where the memory goes, connections to MCP servers on demand, and how to size an instance"
---

MetaMCP itself needs about 200 MB. Most of the memory of an instance goes to the **MCP servers in use**: every connection to a STDIO server is a process, started for a client session. Remote servers (Streamable HTTP, SSE) cost next to nothing.

Measured with the Docker image, four STDIO servers (three through `npx`, one through `uvx`):

| Situation | Memory |
|-----------|--------|
| No client | 170-200 MB |
| A client connects and lists tools, prompts and resources | 200-310 MB: no server starts, except those declaring prompts or resources |
| One client session calling the four servers | 410 MB |
| The session stopped calling them for `MCP_CONNECTION_IDLE_TTL` | back to 200-280 MB |

## Servers start for calls only

Clients list tools, prompts and resources as soon as they connect. Instead of starting every server of the namespace to answer, MetaMCP keeps what each server exposed the last time it was listed (its capabilities and full tool definitions, in the database):

- `tools/list` is answered from it for the servers the session has no connection to (26 tools in 90 ms instead of 5 s in the measurement above). A server starts when one of its tools is called.
- `prompts/list` and `resources/list` skip the servers that declare no prompts or resources.
- The snapshot is refreshed whenever a server is listed on a live connection, at most hourly in the background for the servers in use, and dropped when the server's configuration changes.

| Variable | Default | Description |
|----------|---------|-------------|
| `MCP_TOOLS_CACHE_TTL` | `86400000` (24 h) | Milliseconds during which a snapshot answers for its server. `0` asks the servers every time |

Servers that forward client headers are always asked: their answer may depend on the client's credentials. The snapshot can be out of date in two cases, which then show as an error when a tool is called rather than as a missing tool:

- a server whose tools change without a change of its configuration (an upgrade through `npx pkg@latest`) is listed with its former tools until its snapshot is refreshed;
- a server that no longer starts is still listed.

## Connections on demand

By default a connection opens when a client first needs a server, and the pool closes what nobody uses:

- A client session that stopped calling a server for `MCP_CONNECTION_IDLE_TTL` gives its connection back; its next call gets one again, transparently (a STDIO server restarts in about a second).
- A connection given back is kept as the server's spare for the same time, so that the next client gets it at once. Then it is closed: an instance without clients runs no MCP server.
- A connection is never released while a request of its session is running.

| Variable | Default | Description |
|----------|---------|-------------|
| `MCP_CONNECTION_IDLE_TTL` | `900000` (15 min) | Milliseconds without use before a connection is released. `0` keeps connections until the client session ends |
| `MCP_WARM_POOL` | `false` | `true` keeps one started connection per server of the namespaces exposed by an endpoint, replaced as soon as a client takes it: instant first calls, one process per server at all times |
| `MAX_CONNECTIONS_PER_SERVER` | `5` | Beyond it, a new session takes over the connection of the session that used the server least recently (one is shared only while every holder has a request running) |
| `MAX_TOTAL_CONNECTIONS` | `100` | Ceiling on all connections |

<Warning>
A server that keeps state in memory (a browser automation session, a conversation history) loses it when its connection is released. Raise `MCP_CONNECTION_IDLE_TTL`, or set it to `0`, if your clients rely on such state across long pauses.
</Warning>

Connections to remote servers are released the same way; getting one again only costs a new MCP handshake.

## Launchers: `npx` and `uvx`

`npx -y <package>` and `uvx <package>` stay alive next to the server they start: about 80-120 MB for `npm exec` (twice as much when it has just installed the package) and 60-75 MB for `uv`, per connection, and each start pays for their package resolution (1 to 10 s).

Once a server has started through one of them, MetaMCP reads the program they ran (from `/proc`) and starts that program directly for the next connections: same arguments, environment and working directory, one process instead of two or three, started in 0.2-0.5 s. It goes through the launcher again every 24 hours to pick up package updates, when the server's configuration changes, after a restart of MetaMCP, and whenever the program is no longer where it was (a cleaned cache).

| Variable | Default | Description |
|----------|---------|-------------|
| `MCP_LAUNCHER_BYPASS` | `true` | `false` always starts servers through their launcher. Linux only (the Docker image) |

Two settings help further:

- **Keep the launchers' caches**, so that they do not reinstall packages after a container is recreated: the Docker Compose file persists `/home/nextjs/.npm` and `/home/nextjs/.cache/uv` in volumes (`npm_cache`, `uv_cache`).
- **Preinstall the servers** in an image derived from MetaMCP, and use their executables as commands (`mcp-server-memory` rather than `npx -y @modelcontextprotocol/server-memory`): the first start after a restart is direct too, and the versions are pinned:

```dockerfile
FROM ghcr.io/sixmon/metamcp:latest
USER root
# npm packages: their executables land on the PATH (/usr/bin)
RUN npm install -g @modelcontextprotocol/server-memory@2026.8.31 \
    && npm cache clean --force
# Python tools: in directories the nextjs user can read
ENV UV_TOOL_DIR=/opt/uv-tools UV_TOOL_BIN_DIR=/usr/local/bin
RUN uv tool install mcp-server-time==2026.8.18
USER nextjs
```

Pin the versions: they are what your users run, and upgrading becomes a deliberate change of the image.

## Node.js heaps

Node.js sizes its heaps from the memory of the host, not from what MetaMCP needs. The Docker image caps them, well above the actual use:

| Variable | Default |
|----------|---------|
| `BACKEND_NODE_OPTIONS` | `--max-semi-space-size=4 --max-old-space-size=512` |
| `FRONTEND_NODE_OPTIONS` | `--max-semi-space-size=2 --max-old-space-size=256` |

Flags in `NODE_OPTIONS` take precedence; an empty value falls back to the Node.js defaults. MCP servers never inherit these options. A process that reaches its cap exits with a `JavaScript heap out of memory` error; the container then stops and its restart policy brings it back (`restart: unless-stopped` in the Compose file). Raise the cap if the logs show one.

## Sizing

Count about 200 MB for MetaMCP, plus, for each client session and each STDIO server it calls, 30-60 MB for a server started directly (about 110 MB for a start through `npx`/`uvx`, twice as much while a package installs); heavy servers such as browsers take much more. Servers a session does not call, and sessions left open but unused, cost nothing.

For a team of 3 to 10 people, 2 of them active at a time calling 2 or 3 servers each: 4 to 6 connections, about 450 MB in use and 200 MB at rest. Installing packages is the peak: the very first session of a new instance ran at 1.2 GB while `npx` installed three packages at once. **A 2 GB container limit** covers it, as well as heavier servers. With Kubernetes, set the memory request to the usual level and the limit to the peak (`METAMCP_APP_MEMORY_REQUEST`, `METAMCP_APP_MEMORY_LIMIT`).
