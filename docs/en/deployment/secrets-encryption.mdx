title: "Secrets encryption"
description: "Encryption at rest of stored credentials, with an optional OpenBao / Vault key"
---

MetaMCP stores credentials so that it can connect to MCP servers on behalf of its users. They are protected at rest in two ways:

| Data | Protection |
|------|------------|
| MCP server URLs, arguments, environment values, headers and bearer tokens | **Encrypted** (AES-256-GCM) |
| Upstream OAuth tokens, client registrations and PKCE verifiers | **Encrypted** (AES-256-GCM) |
| Identity provider tokens stored at sign-in | **Encrypted** (by better-auth) |
| API keys | **Fingerprint only** (SHA-256): shown once at creation |
| MetaMCP OAuth access tokens, refresh tokens, authorization codes and client secrets | **Fingerprint only** (SHA-256) |

Names stay readable (environment variable and header names) so that people who can only *use* a server still see which variables it defines, never their values.

## How it works

MetaMCP uses **envelope encryption**:

1. Values are encrypted with a **data key** (256-bit, AES-256-GCM, a fresh IV per value, bound to the field it belongs to).
2. Data keys are stored in the `encryption_keys` table, **wrapped** by a **key encryption key** that never touches the database:
   - a local key from `SECRETS_ENCRYPTION_KEY` (recommended), or
   - a key in **OpenBao / HashiCorp Vault Transit** (optional), or
   - as a fallback, a key derived from `BETTER_AUTH_SECRET`.
3. At startup MetaMCP unwraps its data keys once and keeps them in memory.

A database dump or backup alone is therefore not enough to read stored credentials.

<Warning>
Back up the key encryption key (`SECRETS_ENCRYPTION_KEY`, or the OpenBao Transit key) **separately** from the database. Without it, stored credentials cannot be decrypted: they would have to be entered again.
</Warning>

## Local key (recommended default)

Generate a key and pass it to the backend, for example through your secret store:

```bash
openssl rand -base64 32
```

```bash
SECRETS_ENCRYPTION_KEY=<32 random bytes, base64 or hex>
# or, from a mounted secret (Docker / Kubernetes secrets):
SECRETS_ENCRYPTION_KEY_FILE=/run/secrets/metamcp-encryption-key
```

Without `SECRETS_ENCRYPTION_KEY`, MetaMCP derives a key from `BETTER_AUTH_SECRET` and shows a warning on **Settings → Encryption at rest**. It works, but both secrets can then no longer be rotated independently. In production, MetaMCP refuses to start while `BETTER_AUTH_SECRET` has a placeholder value of the example configurations.

<Warning>
Keep the key out of the database server. The provided `docker-compose.yml` only passes the `POSTGRES_*` variables to Postgres: a key in its environment could be read by any database superuser session, which would defeat the purpose.
</Warning>

## OpenBao / Vault Transit (optional)

With OpenBao, the master key never leaves OpenBao: MetaMCP only asks it to wrap or unwrap its data keys, at startup and when keys are rotated. Once started, an OpenBao outage does not affect MetaMCP. The same configuration works with HashiCorp Vault.

<Steps>
  <Step title="Create the Transit key">
    ```bash
    bao secrets enable transit
    bao write -f transit/keys/metamcp
    ```
  </Step>
  <Step title="Grant MetaMCP the minimum it needs">
    ```hcl
    # metamcp.hcl
    path "transit/encrypt/metamcp" { capabilities = ["update"] }
    path "transit/decrypt/metamcp" { capabilities = ["update"] }
    # Optional: lets MetaMCP move its keys to new Transit key versions
    path "transit/rewrap/metamcp"  { capabilities = ["update"] }
    ```
    ```bash
    bao policy write metamcp metamcp.hcl
    ```
  </Step>
  <Step title="Choose an authentication method">
    AppRole (recommended outside Kubernetes):
    ```bash
    bao auth enable approle
    bao write auth/approle/role/metamcp token_policies=metamcp token_ttl=15m
    bao read auth/approle/role/metamcp/role-id
    bao write -f auth/approle/role/metamcp/secret-id
    ```
    On Kubernetes, use the Kubernetes auth method with a role bound to MetaMCP's service account. A static token (`OPENBAO_TOKEN`) also works.
  </Step>
  <Step title="Configure MetaMCP">
    ```bash
    SECRETS_PROVIDER=openbao
    OPENBAO_ADDR=https://openbao.example.com:8200
    OPENBAO_ROLE_ID=...
    OPENBAO_SECRET_ID_FILE=/run/secrets/openbao-secret-id
    ```
  </Step>
</Steps>

| Variable | Default | Description |
|----------|---------|-------------|
| `SECRETS_PROVIDER` | `local` | `local` or `openbao` (`vault` is an alias) |
| `OPENBAO_ADDR` | | OpenBao / Vault address (`VAULT_ADDR` also accepted) |
| `OPENBAO_NAMESPACE` | | Namespace, if you use them |
| `OPENBAO_TRANSIT_MOUNT` | `transit` | Mount path of the Transit engine |
| `OPENBAO_TRANSIT_KEY` | `metamcp` | Name of the Transit key |
| `OPENBAO_ROLE_ID`, `OPENBAO_SECRET_ID` (or `OPENBAO_SECRET_ID_FILE`) | | AppRole credentials |
| `OPENBAO_APPROLE_MOUNT` | `approle` | AppRole mount path |
| `OPENBAO_K8S_ROLE` | | Kubernetes auth role |
| `OPENBAO_K8S_MOUNT` | `kubernetes` | Kubernetes auth mount path |
| `OPENBAO_K8S_TOKEN_PATH` | service account token | JWT used to log in |
| `OPENBAO_TOKEN` (or `OPENBAO_TOKEN_FILE`) | | Static token (`VAULT_TOKEN` also accepted) |
| `OPENBAO_TIMEOUT_MS` | `10000` | Timeout of each OpenBao request |

For a private certificate authority, add it with Node's standard `NODE_EXTRA_CA_CERTS=/path/to/ca.pem`.

If OpenBao is sealed or unreachable at startup, MetaMCP retries for about a minute, then exits with a clear error rather than running without its keys.

## Rotation

- **Local key**: set the new key in `SECRETS_ENCRYPTION_KEY` and the old one in `SECRETS_ENCRYPTION_KEY_PREVIOUS` (comma-separated), restart: data keys are re-wrapped automatically. Then remove the previous key.
- **OpenBao key**: `bao write -f transit/keys/metamcp/rotate`. At the next start MetaMCP re-wraps its data keys with the newest version, after which old versions can be retired with `min_decryption_version`.
- **Switching provider** (local → OpenBao or back): configure the new provider while the previous key is still available, restart once, then remove the previous configuration.
- **Data key**: **Settings → Encryption at rest → Rotate the data key**. The new key becomes active after `SECRETS_KEY_ACTIVATION_DELAY_SECONDS` (150 s by default, so that every instance loads it first; keep it above 60 s with several instances), then every stored secret is re-encrypted. Nothing stops working in the meantime.

While running, instances only take over new data keys wrapped by their current key encryption key; keys wrapped by an older or fallback key are only taken over at startup. Someone able to write to the database therefore cannot plant a data key protected by a weaker, retired key and have it used for new secrets.

Every rotation is recorded in the [activity log](/en/concepts/activity-log).

## Upgrading an existing instance

- At the first start, values stored in clear text are encrypted with the new data key (and at every start, anything left over). A value that cannot be decrypted with the configured keys (a database restored with another key set, a row edited by hand) is reported in the logs and left as is, without stopping the others.
- Existing API keys keep working, but can no longer be displayed: only their preview (`sk_mt_AbCd…wxyz`) remains. Keys provisioned with `BOOTSTRAP_API_KEYS` accept a `key` value (for example from your secret store). Generated ones are never written to the logs: set `BOOTSTRAP_API_KEYS_FILE` to receive them in a file readable by the service account only (mode 0600), otherwise entries without `key` are skipped.
- Tokens issued by MetaMCP's OAuth server keep working (their fingerprints are computed by the migration); pending authorization codes are dropped.
- Identity provider tokens stored in clear text are removed; they come back, encrypted, at the next sign-in.
